certifique-se de que agora iremos fazer essa arquitetura:

Fluxo de Vida de uma Conexão: Do Diagnóstico à Execução

Vamos detalhar cada passo que o sistema executa.

Fase 1: O Hub Central e o Adaptador Genérico (A Fundação)

Antes de tudo, você precisa construir os dois componentes principais.

A. Requisitos do "Hub Central" (Backend NestJS)

Módulos Principais: AuthModule: Gerencia usuários (JWT, OAuth). OrchestratorModule: Onde vive o Agente LLM (recebe POST /orchestrate). ProvisionerModule: Serviço responsável por "falar" com seu sistema de contêineres (Docker, Kubernetes) para iniciar/parar Adaptadores. Banco de Dados do Hub (PostgreSQL): Tabela users: Padrão. Tabela connections: O "inventário" de conexões. id (uuid), userId (fk) nomeAmigavel (string) status (enum: DIAGNOSING, PENDING_VALIDATION, PROVISIONING, ACTIVE, INACTIVE, ERROR) adapterType (enum: REST, POSTGRES) adapterUrl (string, nullable): A URL interna do microsserviço (ex: http://conn-trello-user1.internal-net) encryptedCredentials (string): O JSON de credenciais (token, user/pass) criptografado. draftSpecification (jsonb, nullable): O "rascunho" do OpenAPI gerado pelo diagnóstico. finalSpecification (jsonb, nullable): O OpenAPI aprovado pelo usuário.

B. Requisitos do "Adaptador Genérico" (Servidor Node.js Separado)

Objetivo: Ser uma imagem Docker "burra" que se configura na inicialização. Configuração (via Variáveis de Ambiente): ADAPTER_TYPE: REST ou POSTGRES ENCRYPTED_CREDENTIALS: A string criptografada (o Adaptador recebe a chave de descriptografia para lê-la). CONNECTION_SPEC: A string JSON da finalSpecification (o OpenAPI aprovado). Lógica na Inicialização (onModuleInit): Lê as variáveis de ambiente. Descriptografa as ENCRYPTED_CREDENTIALS. Parseia a CONNECTION_SPEC. Constrói um Mapa de Ferramentas em Memória: Se REST: Mapeia operationId -> { method, path, params }. Se POSTGRES: Faz introspecção e armazena o esquema. API Padrão (que ele expõe para o Hub): GET /schema: Retorna um JSON padronizado das "ferramentas" que ele aprendeu. (ex: [{ name: "get_boards", description: "..." }]). POST /execute-tool: Recebe {"toolName": "...", "parameters": {...}}. Consulta seu mapa de memória. Usa as credenciais para fazer a chamada real à API externa (ex: axios.get(api.trello.com/...)). Retorna o JSON bruto da API externa. GET /health: Endpoint de health check.

Fase 2: O Pipeline de Diagnóstico Progressivo (O "Agente-Engenheiro")

Este é o processo assíncrono que começa quando o usuário preenche nomeAmigavel, baseUrl e credenciais. Gatilho: POST /api/v1/connections no Hub Central. Ação: O Hub salva a conexão com status: 'DIAGNOSING' e inicia um job de background. Lógica do Job de Diagnóstico: Passo 1: Teste de Tipo (API vs. DB) A baseUrl é uma string postgres://...? Se SIM (Banco de Dados): Chama o "Agente de Introspecção de DB". Ele conecta, roda queries no information_schema e gera um "esquema-MCP" (um JSON simples). Salva este JSON no campo draftSpecification. Muda o status para PENDING_VALIDATION. (Fim do pipeline de DB) Se NÃO (API REST): O pipeline continua. Passo 2: Tentativa de OpenAPI Oficial (Modo 1 - A Fonte da Verdade) O Agente tenta GET em baseUrl/openapi.json, baseUrl/swagger.json, baseUrl/api-docs. Se encontrar, armazena este JSON como spec_base. Passo 3: Tentativa de Documentação + LLM (Modo 3 - O Enriquecimento) O Agente tenta GET em baseUrl/docs, baseUrl/ (e opcionalmente faz uma busca no Google por "docs {baseUrl}"). Se encontrar texto, envia ao LLM com um prompt especial: "Você é um Engenheiro de API. Analise este texto de documentação. Gere uma especificação OpenAPI 3.0 (JSON) dos endpoints. Importante: Você também está recebendo uma spec_base (OpenAPI) existente. Sua tarefa é FUNDIR os dois: use a spec_base como fonte primária e apenas adicione endpoints ou descrições que você encontrou no texto, mas que estão ausentes na spec_base. Não duplique ou sobrescreva." O resultado (um OpenAPI maior) é salvo como spec_merged_llm. Passo 4: Tentativa de Adivinhação (Modo 4 Auto - O Descoberto) O Agente itera sobre uma lista de endpoints comuns (ex: /users, /health, /tasks, /products). Para cada GET que retornar 200 OK e ainda não estiver na spec_merged_llm, ele gera um stub OpenAPI (ex: "/users": { "get": { "description": "Descoberto automaticamente" } }). Ele adiciona isso, criando a spec_draft_final. Passo 5: Conclusão do Diagnóstico O Hub salva a spec_draft_final no campo draftSpecification da tabela connections. Ele atualiza o status da conexão para PENDING_VALIDATION.

Fase 3: A Interface de Validação Humana (A "Cura")

Onde: Uma nova página no Hub Central (Frontend), ex: /app/connections/validate/:id. O que faz: O frontend baixa a draftSpecification da conexão. Interface: A UI NÃO mostra o JSON bruto. Ela renderiza uma "Interface de Construtor de Ferramentas" pré-preenchida. Requisitos da UI: Uma lista de todas as "Ferramentas" (endpoints) encontradas. TAG DE ORIGEM: Cada ferramenta deve exibir como foi descoberta: [ OFICIAL ] (do Passo 2) [ IA-DOCS ] (do Passo 3) [ DESCOBERTO ] (do Passo 4) Ações do Usuário (A Cura): Toggle [ Ativar / Desativar ]: Permite ao usuário desabilitar ferramentas que a IA inventou ou que estão erradas. Botão [ Editar ]: Abre um modal para o usuário refinar a ferramenta: Mudar a description (para o LLM usar melhor). Corrigir parameters. Botão [ Adicionar Nova Ferramenta ]: O "Modo Manual" para adicionar endpoints que o pipeline perdeu. Ação Final: O usuário clica em [ Aprovar e Provisionar ]. O frontend envia a "especificação final" (o JSON curado) para o Hub Backend.

Fase 4: O Provisionamento do Adaptador

Gatilho: POST /api/v1/connections/:id/provision (chamado pela Fase 3). Ação: O Hub Backend executa o seguinte: Recebe a finalSpecification (JSON curado). Salva-a na tabela connections. Atualiza o status para PROVISIONING. Chama o ProvisionerModule com os dados: Imagem Docker: mcp-adapter:latest Credenciais: encryptedCredentials da conexão. Especificação: finalSpecification da conexão. O ProvisionerModule "fala" com seu orquestrador (ex: Kubernetes API) para criar um novo Deployment ou Container. O orquestrador inicia o Adaptador Genérico. O Adaptador, ao iniciar, lê suas variáveis de ambiente, configura-se e expõe sua API interna (/schema, /execute-tool). O Hub Backend salva a adapterUrl (ex: http://conn-id-123.internal-net) no DB. O Hub atualiza o status para ACTIVE.

Fase 5: O Fluxo de Execução (O Loop Final)

Usuário (Chat): "Meus quadros no Trello e clientes da loja". Hub (Orquestrador): Busca todas as conexões ACTIVE do usuário. Chama GET /schema em todos os adapterUrl ativos (em paralelo). Coleta todas as listas de ferramentas. Hub (LLM): Constrói o System Prompt com o Dicionário de UI e a lista de ferramentas fundida (ex: trello_get_boards, db_get_clients). LLM: "Eu preciso chamar trello_get_boards() e db_get_clients()". Hub (Tool Executor): Mapeia: trello_get_boards -> adapterUrl-trello, db_get_clients -> adapterUrl-db. Chama (em paralelo): POST http://adapterUrl-trello/execute-tool (body: { "toolName": "get_boards" }) POST http://adapterUrl-db/execute-tool (body: { "toolName": "get_clients" }) Adaptadores (Trello e DB): Cada um recebe sua chamada. Cada um consulta seu mapa de memória interno. Cada um faz a chamada externa (para api.trello.com e para o DB da loja). Retornam o JSON bruto para o Hub. Hub (Orquestrador): Coleta os dois JSONs brutos. Envia de volta ao LLM: "Aqui estão os dados. Construa a UI." LLM: Retorna o layoutJson final. Hub (Frontend): Renderiza a UI.
